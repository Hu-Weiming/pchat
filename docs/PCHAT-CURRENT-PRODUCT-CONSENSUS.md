# Pchat 当前产品共识

本文记录设计会话中已经确认的系统原则。仍在讨论的内容明确标为“未决”，不得当作实现要求。

## 本轮收敛与推进方式

- 用户要求结束无明确终点的逐项追问，进入系统设计交付。当前无必须补问用户才能编制 Windows MVP 系统设计的阻塞问题。
- 助手负责选择可调整的工程默认值，并明确区别于用户明确要求；不再让用户逐项决定所有实现细节。
- 遇到进程管理、权限、恢复等棘手设计时，优先查阅 Codex、Claude Code 等成熟产品的官方公开资料和可验证实现；只借鉴适用于 Pchat 的原则，不猜测未公开内部设计，也不机械照搬。
- 当前技术实施基线为 [Pchat 当前 Harness 架构与实施计划](./PCHAT-CURRENT-HARNESS-ARCHITECTURE-AND-IMPLEMENTATION-PLAN.md)，强制运行规则见 [Runtime Invariants](./RUNTIME-INVARIANTS.md)，安全范围见 [Security Threat Model](./PCHAT-SECURITY-THREAT-MODEL.md)。架构审查和 [P0 技术验证](./P0-VALIDATION-REPORT.md) 已完成；旧版系统设计不再保留在当前仓库。
- 项目已进入编码阶段，下一步为 P1 Contracts 与 Headless Harness。知识库资料、实际人物内容、费用配置和朋友试用授权在相应接入或发布阶段解决，不阻塞核心开发。
- 负责人具有 Java 软件工程背景，并将技术实现规划交由助手负责。当前工程组织、阶段任务、依赖关系与验收见 [Pchat 当前 Harness 架构与实施计划](./PCHAT-CURRENT-HARNESS-ARCHITECTURE-AND-IMPLEMENTATION-PLAN.md)。P0 未调用任何付费接口。

## 产品定位

- 产品面向希望快速理解陌生哲学领域的入门者。
- 系统呈现的是受资料约束的思想立场模型，不宣称复活或复制历史人物。
- 目标学习成果是：用户能够说明至少两个立场的结论、前提、核心概念、分歧和文本依据，并知道如何继续阅读原典。
- 首版内容规模按思想阶段资料包计数，上限约为二十个；具体人物和阶段由产品负责人选择。
- 用户自定义人物只预留扩展边界，首版不实现社区或自定义人物功能。

## 模式设计

- 交互模式与知识模式相互独立。
- 交互模式负责单人问答、圆桌、辩论、原典阅读、引导探索和学习出题等流程。
- 知识模式负责回答依据的权限：原典模式仅允许原典支持，推演模式允许原典支持和受约束重构，开放拟构模式额外允许创作性回答。
- 默认使用推演模式；开放拟构必须由用户主动选择。
- 竞争性重构默认提示分歧存在，详细依据和推导按需展开。
- 学习模式要求用户自行组织语言作答，系统检查其概念、立场和证据理解，而不是要求复述标准句。
- 证据不足以回答时，可以推荐用户主动切换开放拟构（cosplay）模式；不得自动切换或把拟构回答标为有原典支持。
- Windows MVP 按用户委托采用单人物问答与手动选择二至三位人物对照。流派用于筛选与组织可选人物，不自动召集整个流派；允许后续调整。自动多轮辩论与学习出题留到后续。

## 会话历史与回顾

- 新加入的思想立场模型可以访问之前的聊天记录作为讨论语境，但必须继续依据自己的思想阶段与资料范围表达立场；其他人物的发言不能替代自己的原典依据。
- 新消息持续追加保存，并记录时间；用户提出按轮保存上下文快照。消息记录、轮次与模型实际输入快照的具体组织方式仍在评审，不把每轮复制完整历史认定为已选实现。
- 同一会话正在回答时，用户仍可发送新消息；每个会话内部严格按提交顺序排队，当前整轮完成后再处理下一条。不同会话允许并行，但必须受全局并发与费用上限控制。队列不是立即追加到正在执行的模型上下文，已收到的待处理消息应先持久保存。
- 外部模型调用可能在程序崩溃时出现“供应商可能已收到请求，但本地没有结果”的不确定状态。系统不得自动重试这类调用；必须提示可能已经产生费用，并由用户明确决定是否重新生成。
- 旧回答保留回答当时实际使用的资料及来源，不随知识库后续更新而静默替换。
- 旧回答必须保存当时实际送给模型的依据片段、来源定位、来源版本和校验信息，不能只保存可能失效的知识库引用。
- 一个用户问题只形成一个 Turn；每位参与人物各自形成一个 RoleRun，全部有效回答收敛后才形成同一 Turn 的立场对照。
- 思想日记明确安排在 MVP 之后，当前只保留设计，不成为 Windows MVP 的交付条件。
- 日记直接依据当天聊天中用户实际表达的内容整理，不从 memory 或短期摘要取材；记录用户提出的问题及明确表达的看法，不评价、不推断思想变化、不生成用户画像。
- 用户可以主动生成当天日记并修改当天正文；历史日记正文只读，用户可以对历史日记追加评论。评论记录并展示自己的发布时间，不冒充日记原日期的表达。
- 日记正文和评论只供用户回顾，不提供给任何哲学家角色，不进入角色上下文、记忆摘要或知识库。
- 自动生成、跨日补生成、日期边界、历史删除和评论编辑规则留待日记阶段设计；此前自动补齐旧日期的建议未获确认。完整的后续阶段设想已移入演示目录归档，不属于当前 MVP 实施入口。

## 资料包原则

- 所有思想阶段共用同一种资料包契约，不为不同人物编写不同的系统流程。
- 每个资料包至少需要标明身份与思想阶段、允许使用的资料范围、适用范围以及确认状态。
- 原典资料用于支持思想家本人的立场；二手研究资料用于呈现解释争议，不得伪装成思想家原话。
- 自动生成的资料包草稿必须与经过人工确认的资料包区分。
- 首版导入资料由产品负责人准备；数据准备不是本次系统设计需要解决的自动化任务。
- 每个思想阶段作为独立角色，拥有独立配置和独立知识库；允许重复保存同一份资料，不采用跨角色共享资料库的方案。
- 独立知识库不意味着复制检索、生成等通用系统逻辑；人物提示规则按下文已确认的三层设计组织，具体文本仍待设计。

### 运行时检索与立场锚点

- 人物身份提示词约束角色，回答从该角色知识库中运行时检索书籍和文章后生成。
- 在原典与推演模式下，身份提示词不能成为未经资料支持的哲学立场来源；开放拟构只能在用户主动选择的知识模式中进行。
- 允许有限次数的补充检索，必须设置终止条件；具体次数和预算尚未决定。
- 不要求人工维护立场锚点；可再生的立场索引或缓存仅作为未来候选优化，不属于已承诺的首版功能。

### 分层提示规则

- 提示规则分为系统规则、人物说明和本次任务三层。
- 系统规则统一维护知识模式、引用要求和资料不足时的行为。
- 人物说明分别描述身份、思想阶段、表达方式与关注问题，不能覆盖系统知识约束。
- 本次任务提供用户问题、参与人物与交互模式。
- 具体提示词内容留待后续设计，本阶段不编写。

## 已确认的客户端与接入路线

- 2026-09-05 技术路线确定调整为 Tauri 2 + TypeScript；此前 Flutter/Dart 决策已由 ADR-0007 取代。React + Vite、Headless Harness、受 Tauri Host 管理的 Windows 后台 Runtime 与最小 Rust Host 已在本轮审查中确认；后台打包和私有通信的具体实现仍由 P0 实测决定。
- 交付顺序仍为 Windows → Android → 线上项目 → 最后考虑苹果端；首版仅交付 Windows，不要求 Windows 与 Android 同期完成。
- 第一阶段先由负责人在自己的 Windows 设备上验证。Android、线上项目与苹果端属于后续阶段；苹果端具体覆盖范围留到该阶段确定。
- 知识库与生成模型仍通过云端接口访问；本地安装不等于离线推理。
- 模型调用必须经过供应商无关的统一模块，由适配器隔离各家请求、流式响应和错误格式。人物配置与知识库不绑定 DeepSeek。
- 首阶段只接入并配置 DeepSeek；以后开放用户填写自己的 API Key、选择受支持的供应商与模型。预留不等于首版已经支持所有供应商。
- 知识库供应商由产品负责人继续考察，本轮不锁定供应商；检索与生成保留独立接入边界。
- 本轮只产出架构规范，不开始编写应用代码。现行详细方案见本文开头链接的 Harness 架构与实施计划；其中标注为建议的细节尚未成为共识。

## 首版范围与待确认项

- 产品暂命名为 Pchat Agent。先完成可下载安装的 Windows 本地 Agent，再按已确认顺序扩展其他端；不得将本地 Agent 简化理解为本机运行的网页应用。本地运行不等于离线，知识库与模型仍使用云端接口。
- Windows 与 Android 共享核心逻辑，界面布局、系统凭证与应用生命周期仍需分别适配；不承诺一键交付且无需双端测试。
- Windows MVP 只提供 Tauri 桌面窗口，不提供系统浏览器入口，也不启动 localhost 网页服务。未来真正开发网页版时再增加网络 transport；当前不购买服务器、不改动博客。
- 首阶段模型使用 DeepSeek，具体型号与参数不在业务逻辑中写死；可接受轻度付费，具体人民币月预算未定。用户之前使用 FastGPT 感觉效果不佳，尚无资料样本或评测能判定原因，不直接认定为平台缺陷。
- 知识库与模型通过外部云端接口访问；软件永远不内置或自动分发任何 API Key，每位用户都必须手动填写。负责人自测使用自己的密钥；朋友测试可由负责人另行提供测试专用密钥，最好一人一个并设置低额度或少量余额，绝不提供长期主密钥。Windows MVP 不为此建设服务器代理。
- 用户已有用于个人博客的腾讯云域名；博客由 Netlify 连接 GitHub 仓库部署，内容为 HTML/CSS 静态页面。未确认现有 Netlify 账户套餐，不假设已经具备适合 Pchat 的后端计算能力。不默认迁移或替换博客，也不预设需要购买新服务器。
- 后续线上部署优先评估具有免费额度的托管方案；免费托管不代表外部模型与知识库免费，具体平台尚未选择。
- 产品整体的多种交互模式按已确定的 Windows MVP 子集分期，不要求首版覆盖全部愿景。
- 数据由产品负责人准备，不等同于检索或生成自动正确；回答支持度的核查流程尚待设计。
- 首个可用交付先供负责人自测；朋友试用同样由用户手动填写负责人另行提供的测试专用密钥。若供应商不能分别限额，只能使用可随时废弃的低风险共享测试密钥；扩大测试范围前重新评估服务端代理。跨设备同步不属于当前 Windows 单端交付要求。

## 引用规则

- 有明确版本和译者信息时，系统可以直接引用对应译文。
- 缺少版本或译者信息但存在稳定原典定位时，系统只能概述，不得用引号伪装成可核验原文。
- 引用优先提供作品、章节、节号或命题号等稳定定位，页码仅作为版本相关的补充。
- 版本和译者信息应尽量从导入资料中提取，不要求用户在每次对话中填写。
