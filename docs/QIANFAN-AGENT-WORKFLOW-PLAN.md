# Pchat 千帆知识库 Agent 工作流方案（待接口接入）

日期：2026-09-17。依据仅为 `D:\kk\pbooking` 的目录名和文件名；**没有读取任何书籍内容**。用户确认目录规则为“类别 → 人物 → 著作”，资料内容已审核，并要求千帆 Agent **生成回答且返回证据**。本方案不改变 Pchat 已确认的知识模式、人物隔离和历史证据规则。

## 资料组织

目录有七个哲学类别，书籍候选约 76 个文件；其中 EPUB、PDF、`MD` 下 Markdown 常为同一作品的不同形态，另有一万多张 SVG 配图及与哲学资料无关的开发文件。导入清单先按类别、人名、作品、语言/译本和来源版本去重；每个作品只选一个经确认的规范版本入库，其余作为备份或不同译本明确分列。图片、转换脚本、网页与 Agent 地图不进入哲学知识库。

**类别是目录与导航，不是人物检索范围。** 每位哲学家按用户确认的思想阶段建立资料包；同一人的多个阶段可以分库，同一阶段的不同著作是该库中的独立文档。当前文件名没有可靠标出所有“思想阶段”，不可据文件名自动拆分阶段。原典与研究材料保留来源类型；需要原典严格检索时，用独立的原典范围或等效的硬过滤，避免研究材料混入。每份文档记录稳定 ID、作品、作者、语言、译本/版本、来源类型及确认版本。

## 一个工作流 Agent 的执行路径

```text
Pchat 冻结本轮的 categoryId + roleId + stageId + knowledgeMode + corpusRevision
  → 千帆工作流 Agent 的开始节点
  → 校验/固定路由（枚举值；未知组合直接拒绝）
  → 对应人物阶段的知识库节点（只选该角色已确认的库）
  → 代码节点：过滤、去重、有限数量选段并保留原文和来源 ID
  → 大模型节点：基于选中证据生成该人物回答，逐项标注证据编号
  → 代码/校验节点：引用编号必须存在、无证据时返回不足
  → 结束节点：直接返回 answer + evidence[] + scope/version/status
```

先按“人物＋阶段”画固定分支。千帆知识库节点可选择多个库，但一个把所有人物库混在一起的节点不能作为人物隔离的保证。若画布不能让分支合流并保留结构化输出，就在分支内放相同的后处理组件，再汇入结束节点；发布前以两位人物互问做串库测试。新增人物只增加固定路由与库绑定，不让模型从全部库中自由选库。

千帆知识库节点支持混合检索、召回数量与重排序，并返回 `segment_id`、`document_id`、`dataset_id`、`content`、文档名等字段；这些字段由检索节点直接传到输出，**不交给大模型重新编造**。[官方节点文档](https://cloud.baidu.com/doc/qianfan/s/umh4su4ju)

初始参数建议混合检索取 8 段、重排序后保留 4–6 段、每本书最多 2 段，后续依据实际召回评测调整。压缩发生在检索结果层：去重并删去低相关的整段，保留所选片段的完整原文、ID 和版本，不让模型摘要替代证据文本。章节/节号能稳定取得时保留；缺少稳定定位和译本信息时仅允许概述。问题改写只使用当前角色可见的已完成会话语境；待处理问题和其他角色资料不进入检索。

## 输出与 Pchat 责任

结束节点采用“直接返回参数值”，建议契约：

```json
{
  "status": "SUPPORTED | INSUFFICIENT | REJECTED",
  "answer": "带 [E1] 等证据编号的千帆回答",
  "categoryId": "固定类别 ID",
  "roleId": "固定人物 ID",
  "stageId": "已确认阶段 ID",
  "corpusRevision": "已确认资料版本",
  "evidence": [
    {
      "evidenceId": "E1",
      "datasetId": "知识库 ID",
      "documentId": "文档 ID",
      "segmentId": "片段 ID",
      "text": "检索节点返回的原始片段",
      "workTitle": "已确认元数据",
      "locator": null,
      "sourceKind": "PRIMARY | RESEARCH"
    }
  ]
}
```

这是**拟定的应用契约**，不是声称千帆现成接口已经按此格式返回。千帆工作流的结束节点支持直接返回参数；发布前必须在控制台调试该输出，再用真实 API 响应固定解析器。[官方结束节点与发布说明](https://cloud.baidu.com/doc/qianfan/s/umh4su4ju)

Pchat 收到后检查：冻结的人物/阶段/库版本一致；每个证据 ID 属于该角色已确认文档；`answer` 只引用实际返回的证据；历史保存当时的原片段、元数据、内容哈希及 Agent 回答。异常、串库或缺证据时失败封闭，不能把 Agent 生成的来源描述当成权威。原典模式只接受原典；推演模式标明推导；开放拟构只能由用户主动选。

千帆负责生成一版有证据的回答。当前 Pchat 的 DeepSeek `ModelPort` 仍负责最终人物表达与会话交互：可以把千帆回答作为**候选表述**与核验后的证据一起送入 DeepSeek，但 DeepSeek 不得新增未经证据支持的事实或伪造引文。千帆回答和最终展示回答分别记录，避免把两次生成混为一次。双模型会增加调用费用和延迟，真实账户验收时测量后再调预算；不承诺自动计费等于无需 API 凭证。

## 验收与下一步

先用每类至少一位人物做控制台调试：本人物问题、另一人物问题、无证据问题、原典/推演模式、版本更新与重复格式文档。通过后发布**一个**工作流 Agent，并记录应用 ID、发布版本与节点输出样例。Pchat 再实现该 Agent 的受限端点调用、流式/非流式解析、取消和未知结果处理，保留原直接检索适配器为可替换方案。千帆官方应用调用文档要求 API Key 鉴权；账户自动扣费不替代接口鉴权，具体接入信息待用户确认方案后提供。[官方应用调用 API](https://cloud.baidu.com/doc/qianfan-api/s/7m7wqq361)

此文档只规定编排与核验，尚未创建或发布千帆 Agent，也未连接真实账户。
