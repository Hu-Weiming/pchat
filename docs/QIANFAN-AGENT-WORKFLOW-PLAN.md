## 职责边界

- **DeepSeek 第一次调用：选路。** 根据当前问题识别需要查证的已登记人物/思想阶段，或先识别流派再映射到具体人物；生成每位人物的中性检索问题。不输出哲学结论，也不扩大用户选择的知识模式。
- **Pchat Runtime：编排与校验。** 只接受人物目录中的 ID，把流派映射为有限的具体人物，冻结本轮人物、知识模式、资料范围与版本；逐人物调用 RAGPort，校验证据和来源，记录外部尝试、费用与快照。
- **百度千帆：纯检索。** 从指定人物的已确认原典范围返回原始文本片段和中性来源元数据；不生成立场、摘要或回答，不代替 DeepSeek 解释文本。
- **DeepSeek 第二次调用：最终回答。** 接收原始片段、证据编号、人物说明和知识模式，解释、比较并回复用户。每个事实性论断必须对应本轮可核验的证据；资料不足时明说不足。

“千帆 API 包装转发”在实现上由 Pchat Runtime 完成：Runtime 分别调用 DeepSeek ModelPort 与千帆 RAGPort，再把经过核验的检索结果装入第二次 DeepSeek 请求。千帆无需持有 DeepSeek Key，也不承担模型代理。百度官方提供独立的[知识库检索 API](https://cloud.baidu.com/doc/qianfan-api/s/5mgq9zd5a)，因此此方案优先用检索接口，不需要为了纯检索再建立带大模型节点的千帆工作流 Agent。

## 一轮请求的顺序

```text
用户问题入会话 FIFO 队列
  → DeepSeek 选路：人物/阶段 ID 或流派 ID + 每人物检索问题
  → Pchat 校验允许清单、数量、用户显式选择和知识模式
  → 为每个人物冻结独立 corpus scope / revision
  → 千帆知识库检索 API：逐人物限定知识库和文档范围
  → Pchat 保留原始片段、来源 ID、版本和内容哈希；去重并编号
  → DeepSeek 最终生成：问题 + 人物规则 + 知识模式 + 编号原文证据
  → Pchat 核验引用并保存答案与 EvidenceSnapshot
```

选路调用属于本轮排队问题的受控执行步骤。它必须在任何检索和最终生成之前结束；选定范围在正式 RoleRun 开始前冻结。同一会话后续排队问题不得参与本轮选路。用户明确选择的人物优先；模型不得换人。若未明确选择，模型只可从已登记清单中选择一至三位。流派是目录和选人线索，不是混合知识库；必须先映射为具体人物/思想阶段，超出数量上限时要求收窄，而不是检索整个流派。选路结果无效或不确定时停止并请求用户选择，不允许猜测库 ID。

每位人物拥有独立资料范围；多人物问题执行多次隔离检索，不能把所有人物库放进一个跨库请求。这一版三个知识模式都只检索已确认的哲学家原典，不检索二手研究资料；推演模式仍以原典为依据，DeepSeek 标明推演；开放拟构只能由用户主动选择。资料和用户问题都按不可信输入处理，不允许检索片段中的指令改写路由或系统规则。

## 固定输入、输出契约（拟定）

第一次 DeepSeek 调用只接收问题、用户显式选择、知识模式和可用目录（人物 ID、阶段 ID、流派 ID），返回严格结构化数据：

```json
{
  "routeType": "PERSONS",
  "schoolId": null,
  "targets": [
    { "roleId": "kant", "stageId": "<已登记阶段>", "searchQuery": "自由与自律的原典论述" }
  ]
}
```

若 `routeType` 为 `SCHOOL`，`schoolId` 必须是已登记流派；Pchat 再映射并校验 `targets`。模型只能提出路由建议，不能输出或决定 `knowledgebaseId`、文档 ID、API 参数、资料版本和知识权限。`searchQuery` 也需要长度限制与内容校验；不通过时使用当前问题作为检索词或停止。角色/阶段与库的绑定由 Pchat 的已确认配置表给出。

逐人物调用千帆检索接口的固定参数形状如下；ID 与文档范围由 Pchat 配置表填入，不从模型输出直接取值。`recall.top_k=8`、最终保留 4–6 段、每书最多 2 段只是首轮调试值：

```json
{
  "query": "<经校验的该人物检索问题>",
  "knowledgebase_ids": ["<该人物阶段的知识库 ID>"],
  "metadata_filters": {
    "condition": "and",
    "filters": [{ "field": "doc_id", "operator": "in", "value": ["<已确认原典文档 ID>"] }]
  },
  "recall": { "type": "hybrid", "top_k": 8 },
  "rerank": { "enable": true, "top_n": 6 },
  "top_k": 6,
  "enable_graph": false,
  "enable_expansion": false
}
```

千帆返回的片段只作为数据。Pchat 为每段保存原始 `text`、知识库/文档/片段 ID、著作/译本/定位、来源版本和哈希；不在中途改写为“康德认为……”之类的立场句。若版本或稳定定位不足，不把文本作为可核验逐字引文。检索结果为零时不调用最终生成来编造有依据的回答；返回资料不足，并允许用户主动改选知识模式。

第二次 DeepSeek 调用接收每位人物分组的编号原文证据。系统规则要求：区分原典内容、模型解释和推演；引用仅使用已给编号；跨人物比较不得让甲的证据支持乙的立场；开放拟构不能伪装成原典结论。最终返回的答案与证据列表分开存储；Pchat 校验引用编号、人物归属和知识模式，并保留本次真实发送给模型的证据快照。

## 与现有工程的差距

现有 `QianfanRAG` 已调用千帆独立检索接口并返回原始片段，`RoleExecutor` 已按人物执行“RAG → Model”，因此**不需要改成千帆 Agent 生成回答**。现有配置仍允许研究资料进入部分模式，实施本方案时须收紧为所有模式只检索原典。新增的另一块是第一次 DeepSeek 选路与其结构化契约、外部尝试记录、FIFO/停止/恢复状态、费用预算及无效路由处理。它应放在 Pchat 编排层、复用 ModelPort 的供应商连接，不把 DeepSeek 或百度逻辑写进 Harness 核心。选路未完成之前不能创建或启动使用未冻结范围的 RoleRun；具体状态迁移需要测试驱动调整。

验收至少包括：显式选人不被覆盖；自动选路仅从登记清单取一至三位；流派正确映射且不串库；千帆只返回原文及来源；零证据不伪造答案；跨人物引用不得错配；停止和崩溃后不自动重试结果未知的付费调用；队列内后续问题不泄露给当前选路。真实账号与文档尚未连接，本方案不宣称在线验收通过。
